7. Testing

Software testing is the process of evaluating and verifying that a software product or application does what it is supposed to do. The benefits of testing include preventing bugs, reducing development costs, and improving performance.

For the Havilah project, testing is required to ensure that the user interface is responsive and accessible, and that all critical user interactions—such as form submissions, email notifications via the Resend API, and chatbot interactions—function correctly without failure. The primary objective is to validate that the application meets both its functional requirements (e.g., successful form submissions) and non-functional requirements (e.g., fast load times, mobile responsiveness).

The testing strategy for Havilah focuses on Black-Box Testing, specifically covering Unit Testing for individual UI components, Integration Testing for frontend-to-API communication, and System/Acceptance Testing for end-to-end user workflows. The testing environment utilizes standard modern web browsers (Chrome, Safari, Firefox) on both desktop and mobile platforms.

Note: As identified in the current implementation, the Havilah project is a stateless frontend application built with Next.js, relying entirely on external APIs (like Resend) for data transmission. There is no active database, authentication system, or user management module currently implemented in the repository.

Havilah Testing Strategy Flow

7.1 Unit Testing

Description & Introduction

What is Unit Testing? Unit testing is a software testing method where individual units or components of a software application are tested in isolation. The purpose is to validate that each atomic part of the code performs strictly as designed, independent of other modules.

Relevance to Havilah: In the Havilah project, unit testing is highly relevant because the architecture relies heavily on reusable React UI components (like Forms, Modals, Navbars) and isolated Next.js API route handlers. By rigorously testing these independent components (e.g., verifying that a form correctly flags an invalid email before sending any data), we ensure foundational stability and prevent corrupt data from progressing further down the application flow.

7.2 Integration Testing

Description & Introduction

What is Integration Testing? Integration testing is the phase where previously isolated units are combined and tested together. Its primary purpose is to expose defects in the interfaces and communication pipelines between different modules.

Relevance to Havilah: Havilah relies on a decoupled architecture where the client-side React frontend must serialize and transmit data securely to the server-side Next.js API routes, which in turn must communicate with third-party external services (like the Resend Email API). Integration testing validates these critical hand-offs—ensuring that JSON payloads are correctly parsed, API responses are handled gracefully by the UI, and network failures are caught without crashing the application.

7.3 System Testing

Description & Introduction

What is System Testing? System testing evaluates the complete, fully integrated software application to verify that it meets the specified requirements. Unlike lower-level tests, system testing examines the software from an end-to-end perspective, identical to how a user or external environment interacts with the final product.

Relevance to Havilah: For Havilah, system testing is vital to guarantee smooth user journeys. It ensures that navigating through the site on various devices feels intuitive, animations trigger smoothly on scroll, SEO components correctly render for search engines, and multi-step workflows (like finding a service and booking an appointment) complete without friction across the entire architectural stack.

7.4 Acceptance Testing

Description & Introduction

What is Acceptance Testing? Acceptance testing is the final phase of functional software testing, performed to determine whether the system satisfies the overarching business requirements and client needs. It evaluates the application strictly from the perspective of an end-user.

Relevance to Havilah: While previous tests verified code mechanics, acceptance testing asks: "Can a real potential client use Havilah to achieve their goals?" We test whether a user can intuitively discover services, be captivated by the cinematic portfolio, seamlessly book an appointment, and read the site in their preferred language. If these workflows introduce friction, the software fails its primary business objective.

7.6 Test Data

Because Havilah currently functions as a public-facing portfolio and inquiry generation platform without a database, test data is primarily used within forms and API payloads.

  • Valid data: Standard names ("Jane Doe"), proper email formats ("jane@example.com"), standard phone numbers.
  • Invalid data: Strings without "@" for emails ("janeexample.com"), empty strings for required fields.
  • Boundary data: Extremely long strings (e.g., 5000 characters) in the Contact "Message" field to test layout overflow and API limits.
